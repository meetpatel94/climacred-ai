# ClimaCred AI - Test Data Pack: Testing Guide

**What this is.** A fictional, internally cross-consistent test data set for exercising the whole
ClimaCred AI workflow end to end: business profile, climate assessment, climate fingerprint,
energy / water / waste / emissions / mobility / materials analytics, green solutions,
recommendations, scenario simulation, transformation plan, before/after verification, climate
impact report and the Gemini insight + chat layer.

**What this is not.** Every business, address, contact and number is invented for testing. Nothing
here is a real company, a real measurement, an official emission factor, a certification, a
verified carbon credit, a financing approval or a guaranteed saving. Savings, payback and emission
reductions are illustrative estimates produced from a catalog, not commitments.

**Generated by.** `generator/build_test_data.py`, which reads the repository's own climate engine
(`backend/app/climate_engine/`) and reuses the application's emission factors, so the pack cannot
disagree with the app's arithmetic. No application file was modified.

## 3. IMPORTANT: how ClimaCred actually loads data

Read this before trying to "upload" anything. **The application has no XLSX/CSV importer.**
A search of the repository finds no upload endpoint, no file parser and no import UI; data reaches
MongoDB through the API or the UI forms, and readings are read back only through the API.

| Fact you need | Detail |
| --- | --- |
| How data is created | `POST /api/profile` and `POST /api/assessment` (the UI forms call the same) |
| Which user | Every route uses `user_id = "default"` - **one business per database at a time** |
| So this pack is used as | (a) the source of API request bodies, (b) the expected-value reference to compare against what the app computes, (c) the payload for the history-backed endpoints |
| To test a second business | `POST /api/profile/reset` (clears all stored data), or point `MONGODB_DATABASE` at a separate database per business |
| Fingerprint history | `GET /api/climate-fingerprint/history` reads fingerprint *snapshots*; each `POST /api/fingerprint/generate` adds one. Bulk-load the 24-month series from `api_payloads/B00x_mongo_fingerprint_history.json` |
| Forecast / anomaly endpoints | Accept history **in the request body**, so the 24-month file can be fed to them directly (see section 7) |
| Alias routes | Everything under `/api/...` is also mounted under `/api/v1/...`; the solutions API answers on both `/api/solutions/recommendations` (used by the UI) and `/api/green-solutions/recommendations` |

### Recommended load order

```
1. business_profiles.xlsx             (identity first - nothing else resolves without it)
        |
        v
2. climate_assessments.xlsx           (current-state inputs + expected scores)
        |
        v
3. resource / energy / water / waste / emissions / mobility / operations   (detail tables)
        |
        v
4. historical_climate_data.xlsx       (24-month series -> charts, trends, forecasting)
        |
        v
5. green_solutions.xlsx               (catalog)  ->  solution_recommendations.xlsx
        |
        v
6. scenarios.xlsx  ->  transformation_plans.xlsx  ->  before_after_impact.xlsx
        |
        v
7. Gemini tests: gemini_ai_test_questions.xlsx + gemini_expected_behaviors.xlsx
```

### Dependency map

| File | Depends on | Everything downstream that breaks if it is wrong |
| --- | --- | --- |
| business_profiles | - | assessment, all monthly tables, history |
| climate_assessments | business_profiles | fingerprint, recommendations, scenarios, plan, report |
| resource_consumption | business_profiles | emissions, energy, water, waste, operations, history |
| energy_data | resource_consumption | scope 2 emissions, renewable share, energy score |
| water_data | resource_consumption | water score, water-reuse recommendations |
| waste_data | resource_consumption | waste score, circularity scenarios |
| emissions_data | resource_consumption + energy_data + mobility_data | emissions score, report |
| mobility_data | resource_consumption | scope 1/3 transport, mobility score |
| operations_materials | resource_consumption | material efficiency, recycled-input claims |

## 7. Test 4 - historical trends (24 months)

`historical_climate_data.xlsx` holds 120 rows (5 businesses x 24 months, 2024-09 to 2026-08).

**A. Feed the forecast endpoint directly** (it takes history in the body, so no import is needed):

```bash
python3 - <<'PY'
import csv, json, urllib.request
hist = [{'month': r['month'], 'consumptionKwh': float(r['electricity_kwh'])}
        for r in csv.DictReader(open('csv/historical_climate_data.csv'))
        if r['business_id'] == 'B003']
body = json.dumps({'historical_data': hist, 'metric_key': 'consumptionKwh', 'periods': 3}).encode()
req = urllib.request.Request('http://localhost:8000/api/climate-fingerprint/forecast', body,
                             {'Content-Type': 'application/json'})
print(json.load(urllib.request.urlopen(req))['trend_slope'])
PY
```

The engine needs at least 8 observations; with 24 supplied it returns a real slope and forecast.
Send only 6 rows and it must answer `status: insufficient_data` instead of inventing a trend.

**B. Load the 24 fingerprint snapshots** so the historical chart on the fingerprint page has a real
series:

```bash
mongosh climacred --eval "
  const fs = require('fs');
  const pack = JSON.parse(fs.readFileSync('api_payloads/B003_mongo_fingerprint_history.json'));
  db.climate_fingerprints.deleteMany({data_origin: 'climacred_test_data_pack'});
  db.climate_fingerprints.insertMany(pack.documents);
"
curl 'http://localhost:8000/api/climate-fingerprint/history?limit=24'
```

Every snapshot carries `data_origin: "climacred_test_data_pack"`, so test data is always
distinguishable from anything a user entered, and `deleteMany` on that marker removes exactly the
test data and nothing else.

**C. What the trends should look like**

| Business | 24-month climate score | Story |
| --- | --- | --- |
| B001 | 44.8 -> 38.6 | High-water / high-emissions business with worsening performance |
| B002 | 56.6 -> 56.0 | High-diesel / high-logistics business, mildly worsening |
| B003 | 60.2 -> 70.4 | High organic waste, strong recycling, clearly improving |
| B004 | 78.8 -> 85.2 | Relatively efficient business, strong recycling, improving |
| B005 | 47.9 -> 42.4 | High energy per employee, zero renewables, worsening operations |

The movement comes from real drivers, not noise: B003 gains when the ultrafiltration loop is
commissioned (2024-12), rooftop solar arrives (2025-02) and organic recovery rises; B004 gains
when rainwater harvesting (2025-01) and solar (2025-06) come online; B001 loses ground when leakage
frequency rises (2025-08), ETP performance drops to primary settling (2025-11) and dry recycling
falls below 25% (2026-02); B005 loses ground when leakage becomes frequent (2025-05) and segregation
is discontinued (2025-09). Expect visible step changes, not smooth lines.

## 8. Test 5 - recommendations

`solution_recommendations.xlsx` has 28 rows (B001: 6, B002: 6, B003: 6, B004: 4, B005: 6)
and every recommendation is tied to a metric from that business's own tables, e.g. B001 priority 1:

```
sol-leak-sensors  (Smart Ultrasonic Water Leak & Flow Telemetry)
  reason          : Leakage frequency is reported as 'Monthly' on 4,803,700 L/month of intake.
  baseline metric : 4,803,700 L/month; 0.0% reuse
  capex / savings : INR 298,000 / INR 172,000 per year
  payback         : 20.8 months (estimate)
  addresses       : Water (score 10.0/100)
```

How priority is derived: `score = 0.50 x severity + 0.30 x financial + 0.20 x environmental`, where
severity = `1 - dimension_score/100` for the dimension the solution addresses. Priority 1 must
address one of the business's three weakest dimensions - the validator enforces this. The pack's
ordering is therefore defensible from the data, while ClimaCred's own engine uses its own weights
(`impact 0.30, financial 0.25, environmental 0.20, feasibility 0.15, relevance 0.10`), so **compare
the reasoning, not the exact rank order**.

Catalog economics are scaled to each business (`scaling_basis` column, factor 0.35-1.60) because the
app catalog ships reference sizes - a 75 kWp solar system priced for a large plant. The app returns
the unscaled catalog values, so this too is a "shape, not exact figures" comparison.

## 9. Test 6 - Scenario Simulator

`scenarios.xlsx` has 35 rows: 7 scenarios per business.

| Scenario | Contains |
| --- | --- |
| Current Baseline | nothing - all zeros (the control row) |
| Solar Scenario | rooftop solar |
| Energy Efficiency Scenario | VFD/motors, LED, sub-metering, plus compressed-air or HVAC where relevant |
| Water Efficiency Scenario | leak telemetry, rainwater, water recycling, ETP optimisation - filtered to the business's actual water profile |
| Waste Circularity Scenario | segregation, material recovery, composting, packaging - filtered to the business's streams |
| Green Mobility Scenario | route optimisation and EV transition - filtered to the fleet's fuel volume |
| Combined Transformation Scenario | the union of the six above |

Because the combined scenario is the **union**, it is guaranteed to be at least as large as any
single scenario, and the transformation plan totals tie to it exactly (plan cost = combined capex + INR 180,000 verification action). Both facts are asserted by the validator.

Check by hand on any row: `payback_years = capex / annual_cost_savings`, and
`projected_5_year_savings = 5 x (annual_cost_savings - annual_operating_cost_change) - capex`.
The 5-year figure is deliberately a simple undiscounted sum of estimates - it is not a financial
model and must never be presented as a return guarantee.

In the app: pick the corresponding solutions in the Scenario Simulator and compare direction and
magnitude with the row for that business. Baseline annual electricity, water and emissions are
included as columns so you can sanity-check any percentage the app or Gemini quotes.

## 10. Test 7 - Transformation Plan

`transformation_plans.xlsx` has 65 rows covering all five phases for
every business.

| Phase | Contents | Typical timing |
| --- | --- | --- |
| Phase 1 - Quick Wins | segregation, route optimisation, leak telemetry, LED | months 1-3 |
| Phase 2 - Efficiency Improvements | VFD/motors, sub-metering, compressed air, HVAC, rainwater, ETP optimisation | months 4-7 |
| Phase 3 - Circularity | material recovery, composting, material reuse, sustainable packaging | months 8-11 |
| Phase 4 - Renewable / Mobility Transition | rooftop solar, heat recovery, EV fleet | months 12-14 |
| Phase 5 - Verification | metering calibration, reconciliation, third-party review | month 15+ |

`start_month` and `duration_months` are laid out sequentially inside each phase, so no two actions
in the same phase can start before the previous one finishes; `dependency` states what must be true
first (for example solar needs a roof structural survey and a net-metering application).

Note: ClimaCred's own generated plan uses **four** phase names
(Phase 1 Immediate Low-Hanging Actions, Phase 2 System Efficiency Improvements,
Phase 3 Capital Green Investments, Phase 4 Impact Verification & Continuous Intelligence).
This pack uses the five-phase structure requested for testing; map Phase 1->1, Phase 2->2,
Phase 3->3+4, Phase 4->5 when comparing.

`status` is `Completed` in Phase 1 and `In Progress` in Phase 2 for exactly B001, B003 and B004 -
the three businesses that also have before/after rows - so the plan, the impact page and the
history tell one story.

## 11. Test 8 - Before/After impact verification

`before_after_impact.xlsx` has 30 rows = 3 businesses x 10 metrics.
Windows: baseline `2025-03` to `2025-08` vs post-intervention `2026-03` to `2026-08`, both averaged
from the same monthly model as every other file.

**Sign convention:** `improvement_percent` is the *favourable* change, so positive always means
better, whichever direction the metric moves. `direction` repeats the rule in words. Example - B001:

| Metric | Baseline | After | Favourable change | Reading |
| --- | --- | --- | --- | --- |
| Electricity consumption | 297560 | 270881 | 9.0% | improved |
| Water consumption | 4755859 | 4783720 | -0.6% | flat |
| Waste to landfill | 10802 | 11985 | -11.0% | worsened |
| Recycling rate | 24.7 | 22.0 | -10.9% | worsened |
| Diesel consumption | 2854 | 2992 | -4.8% | worsened |
| Scope 1 emissions | 8.49 | 8.89 | -4.7% | worsened |
| Scope 2 emissions | 244.0 | 222.12 | 9.0% | improved |
| Total emissions | 699.25 | 677.97 | 3.0% | improved |
| Energy intensity | 4.184 | 3.602 | 13.9% | improved |
| Water intensity | 66.89 | 63.6 | 4.9% | improved |

B001 is deliberately a **mixed** result: electricity, energy intensity, water intensity and total
emissions improve while water intake, landfill and recycling rate deteriorate. That is what a
partially executed plan looks like, and it is the case that catches "everything always improves"
wording in the UI or in an AI answer.

`verification_status` reads "Self-reported by business (not third-party verified)" on every row.
The app must mirror that: it may say *observed change* or *reported implementation outcome*, and
must never say *verified carbon reduction*.

## 17. Data model, factors and assumptions

### Emission and cost factors

| Factor | Value | Source |
| --- | --- | --- |
| Grid electricity | 0.82 kg CO2e/kWh | `ELECTRICITY_EMISSION_FACTOR_KG_PER_KWH` in the app config |
| Diesel | 2.68 kg CO2e/litre | `DIESEL_EMISSION_FACTOR_KG_PER_LITRE` |
| Petrol | 2.31 kg CO2e/litre | `PETROL_EMISSION_FACTOR_KG_PER_LITRE` |
| LPG / CNG | 2.75 kg CO2e/kg | The app's configurable gaseous-fuel factor, reused for the tables so the pack and the app agree |
| Water | INR 30 per kL | `WATER_COST_PER_KL_INR` (used for the water-cost columns) |

All of these are configurable application defaults - **not** certified or official values.

### Scope 3 factors (illustrative, same for every business)

| Component | Factor |
| --- | --- |
| Purchased materials | cotton yarn 5.90, steel 2.10, agri produce 0.55, kraft paper 1.05, polymer 2.40, wood 0.46 kg CO2e/kg |
| Third-party freight | 0.42 kg CO2e/km |
| Employee commuting | 0.053 kg/passenger-km (two-wheeler dominated) or 0.028 (company bus) |
| Business travel | 0.12 kg CO2e/km |
| Waste to landfill | 0.55 kg CO2e/kg |

### Other documented choices

* **LPG** is modelled with the app's gaseous-fuel factor (2.75) rather than the literature value of
  roughly 2.98 kg CO2e/kg, so the pack and the app agree to within rounding. If you change
  `NATURAL_GAS_EMISSION_FACTOR_KG_PER_KG`, regenerate the pack.
* **EV charging kWh is already inside `electricity_kwh` and `grid_kwh`** - it is metered site
  consumption, so counting it again would double-count it.
* **Diesel is split deliberately:** `resource_consumption.diesel_litres` is total diesel purchased,
  `energy_data.diesel_litres` is genset/process diesel and `mobility_data.diesel_litres` is fleet
  diesel. `total = genset/process + fleet` holds in every row (the validator asserts it).
* **Waste is one dataset in two compatible partitions.** Internally there are eight streams
  (organic, plastic, paper, metal scrap, textile/wood material, industrial residue, general,
  hazardous). The assessment form has five boxes, so `industrial` in `climate_assessments` folds in
  industrial residue + general + hazardous, and `textileMaterialWasteKgPerMonth` carries wood
  off-cuts for the furniture business. Section 18 lists the exact identities.
* **Water reuse rate** = `reused / (freshwater_intake + reused) x 100` - reused water is a separate
  loop and is never subtracted from intake.
* **Operating days** follow a real Indian festival calendar (Diwali shutdowns in Nov 2024 /
  Oct 2025, Pongal in Tamil Nadu, Holi in Rajasthan), which is why monthly rows are not flat.
* **`emissions_intensity`** is kg CO2e per production unit (units differ by industry: kg of fabric,
  machined pieces, kg of food, packaging units, furniture pieces).
* **LPG is absent from the app's assessment form** (the nearest field is `monthlyNaturalGasKg`), so
  the assessment payload sends LPG/CNG there; that is what keeps the app's computed emissions equal
  to `scope_1 + scope_2` in the emissions file.

## 19. Where this pack and the application will legitimately differ

Documented on purpose - a difference you can explain is a test result, an unexplained difference is
a bug.

**1. Scope 2 with on-site solar.** ClimaCred's emissions analytics multiply *total* monthly kWh by
the grid factor, so self-consumed solar generation is not netted out. This pack multiplies only
grid kWh. The difference appears only for businesses with solar:

| Business | Solar | App scope 1+2 (tCO2e/month) | Pack scope 1+2 | Difference |
| --- | --- | --- | --- | --- |
| B001 | 0 kWp | 227.09 | 227.094 | -0.004 |
| B002 | 0 kWp | 92.71 | 92.706 | +0.004 |
| B003 | 20 kWp | 116.51 | 115.366 | +1.144 |
| B004 | 48 kWp | 37.54 | 34.264 | +3.276 |
| B005 | 0 kWp | 52.24 | 52.238 | +0.002 |

For B001, B002 and B005 the two agree to within 0.01 tCO2e/month. B003 differs by about 1.1 and
B004 by about 3.3 tCO2e/month - exactly the emissions of the self-consumed solar. Test the emission
pages with the pack's numbers, and use B004 to demonstrate the gap.

**2. Recommendation and scenario economics are scaled** (see section 8); the app returns catalog
reference values.

**3. Priority ordering** uses this pack's documented weights; the app's engine uses its own
(`RECOMMENDATION_WEIGHTS`). Both are transparent; neither is "the truth".

**4. Phase names** differ (4 in the app, 5 in the pack - mapping in section 10).

**5. Material waste field.** The assessment's fifth waste box is implemented as
`textileMaterialWasteKgPerMonth`; for the furniture business this pack puts wood off-cuts there, so
the app applies its textile-specific wording to a wood-working business. Expect odd phrasing, not
wrong arithmetic.

## 21. Assumptions and limits (please read)

1. **All businesses, people, addresses, emails and phone numbers are fictional.** Contact addresses
   use the reserved `.example` domain and the phone number is `+91 00000 00000`, so nothing can reach
   a real inbox or number.
2. **The monthly numbers are modelled, not measured.** They are internally consistent and
   industry-plausible (water per kg of fabric, chips per machined piece, kWh per kg of food), but they
   are not real meter readings and must not be used for any compliance, disclosure or financing
   purpose.
3. **Savings, payback and emission reductions are catalog-based illustrative estimates.** They are
   labelled as estimates in the files (`basis_note`, `estimated_*`). ClimaCred does not certify
   reductions, issue carbon credits or approve financing, and nothing in this pack should be read as
   an offer, a guarantee or an eligibility claim for any subsidy scheme.
4. **`created_at` is the record-creation date in ClimaCred (2026-09), not the year the business was
   founded** (`year_established` covers that). Historical months predate `created_at` on purpose:
   they represent the business's own operating history being loaded into the platform.
5. Amounts in the workbook sheets are plain numbers with the unit stated in the column header
   (`capex` in INR, `annual_water_savings_litres` in litres, and so on); no currency symbols are
   embedded in numeric cells, so they stay machine-readable.
6. Indian financial-year and fiscal-incentive behaviour (tariff slabs, demand charges, net-metering
   rules, subsidy percentages) is out of scope: the pack tests the application's arithmetic and its
   refusal to over-claim, not local policy.
7. **The build is reproducible.** `build_test_data.py` is deterministic (all randomness is seeded
   and every timestamp comes from the modelled month, not the clock), so re-running it reproduces the
   CSV and JSON files byte for byte - you can checksum-verify a pack against a rebuild. The `.xlsx`
   files carry their own ZIP container timestamps, so compare the `csv/` copies if you want an exact
   match. Note that changing a factor in `backend/app/config.py` will change the pack, by design.
8. Regenerate after any change to factors, weights or filters:
   `cd generator && python3 build_test_data.py && python3 validate_test_data.py && python3 build_readme.py`
